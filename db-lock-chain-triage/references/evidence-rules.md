# 证据判断规则与反例

每条规则都来自一次真实误判、差点误判或实测。规则 9、10 是 WorkBuddy 在 2026-10-14 挂载测试中自行补充的，经人工核对后保留。环境：KingbaseES V009R002C014，Oracle 兼容模式，2026 年 9 月。

## 1. 链头要拼出来，不能读出来

2026-09-13 15:36 的现场，三个进程都落在 `yanshi.orders` 中 `order_no = 'SO-2026-0002'` 这一行（行位置 (0,2)）：

| 进程 | 状态 | 等的锁 | 等谁 | 已等 |
|---|---|---|---|---|
| 1004761 | idle in transaction | — | — | — |
| 1005031 | UPDATE waiting | 事务 1668 的 ShareLock | 1004761 | 571.3 秒 |
| 1005115 | UPDATE waiting | 行 (0,2) 的 ExclusiveLock | 1005031 | 541.3 秒 |

1005115 的日志写的是「Process holding the lock: 1005031」，单看这一行会把 1005031 当成元凶。1005031 自己也在等。链头是 1004761，它在日志里没有任何记录，因为它不在等任何人。

规则：日志里没有等待记录、却出现在别人 holding 列表里的进程，优先怀疑是链头。

## 2. 互不相干的链分开报

当天 13:22 第一轮造锁（982015 持锁、982106 等锁）时，同一实例上还挂着一对遗留会话：598712（idle in transaction，持锁）和 598722（UPDATE waiting），锁对象是另一张表 `app_user.tx_lock_demo`，2026-09-12 01:31 连入，已挂约 36 小时，每 30 秒写一行日志，当天写了 1641 行。

不清掉的话，巡检会同时看到两条阻塞链和一个 36 小时的长事务，模型很容易把它们合成一个故事。

规则：按锁对象分组；事务时长比业务正常值高一个数量级以上的，单独标为遗留会话。

## 3. 「看不全」不是「没有」

用只读账号 nlq_reader 巡检，草稿里写着「SQL 因权限不足不可见」「当前连接数为 1」。核实结果：

- 两条阻塞链的 SQL 共 4 处显示 `<insufficient privilege>`
- 连接总数查询带 `backend_type in (...)` 条件，其他账号会话的 backend_type 对 nlq_reader 不可见，只数到 1 个，实际至少 5 个

修法：`GRANT sys_read_all_stats TO nlq_reader;`。《KingbaseES 数据库安全指南》对这个预置角色的说明是可以读取所有 sys_stat_* 视图，包括通常只对超级用户可见的信息。代价是这个账号能看到其他会话正在执行的 SQL 原文，需要 DBA 权衡。

规则：出现 `<insufficient privilege>`，或视图里的连接数明显少于主机进程表，先报「权限不足，结论不完整」。

极端情形是完全连不上库、一条视图都没有（见规则 10）：此时证据只剩日志 + 进程表，结论的覆盖范围必须写在结论里，不能略过。

## 4. 看结果，不看查询文本

故障分析助手早期的判断逻辑：证据文本里只要出现 sys_locks 查询，就判为「检测到锁等待」。每份巡检都带这条 SQL，于是锁已经释放后的「修复后验证」也被判成检测到。同时等锁数只数原始锁行里的 granted=false，巡检汇总里的 `waiting_lock_count = 2` 和阻塞链行都没算，得出 0。

修复后：等锁数取三种写法（汇总计数、阻塞对行数、granted=false 行数）的最大值；只有等锁数 > 0，或日志里出现 still waiting / deadlock / lock timeout 等信号，才判为检测到。4 个用例：

| 证据 | 等锁数 | 检测到 |
|---|---|---|
| 真实巡检 | 2 | 是 |
| 锁释放后的巡检 | 0 | 否 |
| 只有服务器日志 | 0 | 是（日志信号） |
| 原始锁行 granted=false ×2 | 2 | 是 |

## 5. 日志没有记录，不等于没有等待

`still waiting for` 只在实例记录锁等待、并且等待超过阈值后才写。这台实例（V009R002C014）`SHOW log_lock_waits` 是 off，来源是 default，`deadlock_timeout` 是 1s；2026-10-14 实测，等锁约 31 秒时日志里照样写出了 still waiting for。所以要以日志实际内容为准，不要凭参数推断有没有日志。日志为空时，回到 SQL 1、SQL 2 看现场，不能直接下「无锁等待」的结论。

## 6. 处置顺序

链头确定后，建议结束链头（例中 1004761），它未提交的事务会被回滚。

2026-10-14 在同一台 KingbaseES V009R002C014 上复现了同样的三段链（同一行，A ← B ← C，B 等 A 的事务锁，C 等 B 持有的行锁），然后只结束实验会话做对照，见 `samples/kes-v009r002c014-lab-20261014.log`：

| 场景 | 结束谁 | 之后 |
|---|---|---|
| 同一行三段链 | 中间的 B | C 改为等 A 的事务锁，问题不变 |
| 同一行三段链 | 链头 A | B 拿到行锁；C 改为等 B |
| 不同行串成的链 | 中间的 B | C 立刻放行，A 仍持有行 1 |

Oracle 19c RAC 上结论一致（见 `oracle.md`）。所以默认建议结束链头；结束中间会话在同一行排队时没有用，在不同行的链里能放行下游但要回滚一个正常事务，只在 DBA 明确接受这个代价时作为备选。

遗留会话按「先等待方、后持锁方」结束（例中先 598722 再 598712），避免持锁方一释放，等待方的语句立刻执行下去改了数据。

## 7. 工具生成的 kill 名单要核对

Oracle 19c RAC，不同行串成的链 A ← B ← C，同一时刻两条现成 SQL 给出的 kill 名单：

- 按 v$wait_chains 从链头展开（dbatool lsblk）：只有 A
- 按每个等待者的直接阻塞者（dbatool lstx 同款 SQL）：A 和 B

照后一份名单全部执行，会多回滚一个正常事务。这两个命令在生产排障中都常用，用 lstx 的名单之前，要先和 lsblk 给出的链头对一下。

规则：kill 名单只是候选，必须和拼出来的链头核对，名单里的非链头会话要单独说明代价。

## 8. 视图之间会对不上

同一套 Oracle RAC 上：v$wait_chains 已经给出三层链时，gv$session 里两个等待者的 blocking_session 都是空的；另一轮里两个等待者一个有值一个为空。dbatool lstx 原版的 gv$ 查询还报了 ORA-12850，换成本实例 v$ 才跑出结果。

规则：等待事件是锁、但 blocking_session 为空，不能判"没被堵"；工具降级到本实例视图时，结论里写明只覆盖哪个实例。

## 9. 进程表的时长是「分:秒」，不是「时:分」

`ps` 的 etime 不足 1 小时时只有两段，即 `分:秒`。2026-09-13 15:36 现场的 `10:31`、`09:35`、`09:03`，按小时读就是"三个挂了 9–10 小时的会话"，会把一起 10 分钟的阻塞误判成遗留会话批量积压，进而把处置方向带偏到"清理历史长事务"。

判读办法：等待者的进程存活时长应当**略大于**日志里它的等锁时长（建连到卡住之间还有几秒准备），对得上就是分:秒。例中 `09:35` 对 571.3 秒、`09:03` 对 541.3 秒，各差 5 秒左右。

还要分清：etime 是**进程**存活时长，不是事务时长。链头 `idle in transaction` 只给出事务已开启时间的上界（进程建连时刻），下界来自等待者已等的秒数。写结论时用区间表述，不要当成实测的事务时长。

## 10. 一条视图都拿不到时，结论要自带范围声明

本次 15:36 现场连不上库，sys_locks / sys_stat_activity 一条都没取到，证据只剩服务器日志 + 主机进程表。这种情形和规则 3 的权限不足同源：能拼出「看得见的那条链」，但不等于全库只有这一条链。

规则：结论里写明「覆盖范围 = 日志与进程表可见的会话」，把"无法证明没有并存的第二条链"作为显式不确定项列出，不要让读者以为已看全。
