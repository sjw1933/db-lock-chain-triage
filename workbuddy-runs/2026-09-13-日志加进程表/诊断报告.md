# 锁等待链诊断记录：订单支付卡住

## 0. 采集口径

| 项 | 值 |
|---|---|
| 数据库 | KingbaseES V009R002C014，Oracle 兼容模式 |
| 实例 / 库 | 单实例，test 库 |
| 账号 | app_user，客户端 127.0.0.1 |
| 证据时间 | 主机进程表 2026-09-13 15:36:15；服务器日志 15:27:16 – 15:36:18 |
| 库内视图 | **无**（本次连不上库，sys_locks / sys_stat_activity 均未取到） |
| 结论范围 | 仅覆盖「这一条链」；无法证明"只有这一条链" |

> 提示：进程表里的 `已运行 10:31 / 09:35 / 09:03` 是 `etime` 的两段式写法，即 **分:秒**（10 分 31 秒、9 分 35 秒、9 分 3 秒），不是小时。若按小时读，会误把三个会话当成挂了 9–10 小时的遗留会话。两个等待者的进程存活时长（9:35、9:03）与日志里它们的等锁时长（571.3 秒 ≈ 9 分 31 秒、541.3 秒 ≈ 9 分 1 秒）几乎相等，互为印证。

## 1. 结论：一条串行链，链头是 1004761

```
1005115  ──等行锁(0,2)──▶  1005031  ──等事务 1668──▶  1004761  ← 链头（不再等任何人）
UPDATE waiting            UPDATE waiting            idle in transaction
```

三个会话改的是 `yanshi.orders` 中 `order_no = 'SO-2026-0002'` 这**同一行**（行位置 (0,2)）。

| 进程 | 状态 | 等什么 | 等谁 | 最长已等 |
|---|---|---|---|---|
| 1004761 | idle in transaction | — | — | — |
| 1005031 | UPDATE waiting | 事务 1668 的 ShareLock | 1004761 | 571.3 s |
| 1005115 | UPDATE waiting | 行 (0,2) 的 ExclusiveLock | 1005031 | 541.3 s |

**卡住支付的是 1004761。** 它拿着事务 1668 的锁，状态是 `idle in transaction`——锁在手里，人已经不动了。它自己不在等任何人，所以它在服务器日志里**一行记录都没有**。

## 2. 为什么不能顺着日志往下读

日志里 1005115 那行写得很清楚：

```
[1005115] DETAIL:  Process holding the lock: 1005031.
```

只看这一行，元凶就是 1005031。但 1005031 自己也有一条：

```
[1005031] DETAIL:  Process holding the lock: 1004761.
```

1005031 在 15:27:16 就等了 31 秒，15:36:16 已等 571 秒，等待时长在单调增长——它是个等待者，不是持锁不放的人。**链头以"不再等别人"为准，不以等得最久、语句最显眼为准。** 主机进程表也独立印证了这一点：唯一的 `idle in transaction` 就是 1004761。

另一个佐证：1005031 等的是**事务 1668 的 ShareLock**（说明这行已被事务 1668 改过、正在等它结束），而 1005115 等的是**行 (0,2) 的 ExclusiveLock**（说明它排在 1005031 那次进行中的更新后面）。两者等待对象不同，正是链上"前一个已经动了手、后一个还在排队"的表现。

## 3. 时间线

| 时刻 | 事件 |
|---|---|
| 15:25:44 | 1004761 会话建立（进程存活 10:31），事务开始；事务开始语句未知 |
| ~15:26:45 | 1005031 阻塞在事务 1668 上，开始等待（此为该事务已开启时间的下界） |
| 15:27:12 | 1005115 会话建立（进程存活 9:03） |
| ~15:27:17 | 1005115 排在 1005031 后面，开始等待 |
| 15:36:15 | 进程表快照：一个 idle in transaction，两个 UPDATE waiting |
| 15:36:16 / 15:36:18 | 日志最后一次记录，等待仍在增长（571.3 s / 541.3 s） |
| 全程 | 无 `deadlock detected`、无 `lock timeout`、无 `canceling statement` |

等待时长从 31 秒一路涨到 9 分半且无任何终止类信号，说明**这不是瞬时抖动，是一笔会一直挂着的阻塞**（该实例没有生效的 lock_timeout 把它踢出来）。

## 4. 置信度

**链结构与链头：高。** 理由：两条边都有日志里显式的 "Process holding the lock" 支撑，不是靠推测拼的；主机进程表独立给出同向结论（唯一的 idle in transaction 正是链头）。

**为什么不更高：**

1. **没有库内视图。** 无法确认全库只有这三个会话、只有这一条链、没有并存的第二条链和别的锁对象——这是"看不全"，不是"没有"。
2. **链头在做什么，无证据。** 它的 `xact_start` 精确值和最后执行的语句都取不到（日志只记录等待者；本次连不上库）。上表的"事务约 9.5–10.5 分钟"是从"进程存活 10:31"和"1005031 已等 571.3 秒"反推出的区间，不是实测的事务时长。
3. **一个小链接未用元数据确认：** 1005115 那行写的是 `relation 18949`，1005031 那行写的是 `relation "orders"`。OID → 表名的对应关系需要查库确认；两者指向同一行位置 (0,2)、语句也都是同一张表同一订单，推断一致，但严格说未经元数据核实。
4. 连不上库本身可能与连接数被占满有关，属于伴生现象还是独立问题，本轮无证据判断。

## 5. 处置建议（需 DBA 确认后执行）

**建议结束链头 1004761。** 它未提交的事务会被回滚。预计效果：1005031 拿到事务 1668 的锁后继续执行 `status='paying'`，1005115 随后拿到行 (0,2) 的锁继续执行 `status='paid'`，下游一并放行。

执行前先确认一条：**1004761 那笔未提交的事务是不是本该保留的业务数据**。如果是，回滚会造成业务侧数据丢失，此时应先和业务确认怎么补，而不是直接杀。

**不要只结束 1005031。** 它虽然是"改 paying"的那个、看起来最像肇事者，但它不是链头：

- 结束它，1005115 拿到行 (0,2) 的锁后会转去等事务 1668，**问题一点没变**；
- 代价是多回滚一个正常业务事务。
- （这一条在 KingbaseES 上未实测结束会话验证，是按锁排队方式推断；Oracle 19c RAC 上实测结论一致。）

如果拿到过任何自动生成的 kill 名单，**先和上面这个链头核对再用**：同一行排队时，名单里出现非链头会话的那几项都要单独说明代价。

## 6. 下一步只读验证清单

1. 库能连上后，跑 `lock_evidence.sql` 的 SQL 2（阻塞对）和 SQL 3（未结束事务按 xact_start 排序）：确认全库只有这一条链，并拿到 1004761 的真实 `state / xact_start / wait_event`。
2. 采集账号需具备 `sys_read_all_stats` 预置角色，否则别人会话的 SQL 显示 `<insufficient privilege>`、按 `backend_type` 过滤的连接数会偏小，结论会以"看不全"收场。
3. 待验证假设（需要应用日志或业务代码，不在本轮证据范围内）：
   - 1004761 为何停在 idle in transaction——连接池借出连接后未 commit/rollback、应用进程挂起、或手工会话忘了提交；
   - 三个会话是否属于同一笔支付的连续状态流转（paying → paid），若是，则应从业务侧堵住"同一订单被并发会话重复更新"的入口。
4. 预防方向（配置层，由 DBA 评估）：为业务账号设 `idle_in_transaction_session_timeout` 与 `lock_timeout`，让这类挂死的事务自行退出，而不是无限期占锁。
