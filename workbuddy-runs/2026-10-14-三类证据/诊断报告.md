## 二、结论：一条三段串行链，堵点在最前面的 658916

**谁堵住了谁：658916(locklab-A) ← 658918(locklab-B) ← 658917(locklab-C)**
三者排在同一条记录 `locklab_orders.id = 1` 上。

| 位置 | PID | 应用 | 状态 | 在等什么 | 等谁 | 已等 |
|---|---|---|---|---|---|---|
| **链头** | 658916 | locklab-A | idle in transaction | 不等锁（ClientRead） | — | — |
| 中段 | 658918 | locklab-B | active | ShareLock on transaction 1674 | 658916 | ≈ 37s |
| 队尾 | 658917 | locklab-C | active | ExclusiveLock on tuple (0,1) | 658918 | ≈ 35s |

- 不是死锁：没有环，是一条纯等待链（三方同时段均无 deadlock / kill / timeout 类日志信号）。
- 只有一条链：两个阻塞对都在同一锁对象（同 relation、同 tuple、id = 1），按锁对象分组属于同一条链，不是两条。

## 三、证据与交叉印证

**等锁数（三种口径）**：`waiting_lock_count = 2`、阻塞对 2 行，一致且 > 0 → 确认存在锁等待。

**边的一致性**：

| 边 | 日志 | 视图（阻塞对） | 进程表 |
|---|---|---|---|
| 658918 等 658916 | ShareLock on transaction 1674，18:12:55 记录 31.0s | blocking_pid = 658916 | 658918 = UPDATE waiting |
| 658917 等 658918 | ExclusiveLock on tuple (0,1) of relation 19034，18:12:57 记录 31.0s | blocking_pid = 658918 | 658917 = UPDATE waiting |
| 658916 是持锁方 | 出现在 658918 的 "Process holding the lock" 里，自身无等待记录 | idle in transaction | idle in transaction |

三处完全吻合，无多余边、无缺失边。日志脚本单独跑出的结果也是「链头 658916」。

**时长自洽**：事务时长 A 40.0s > B 38.1s > C 36.1s，严格递减、步长约 2s，符合依次入队的顺序。进程表 `ELAPSED = 00:40` 是 **分:秒（40 秒）**，不是 40 分钟；等待者进程存活 40s 略大于其等锁 31s+，对得上。

## 四、链头的性质（关键）

658916 的 `wait_event_type / wait_event` 是 `Client / ClientRead` —— 它在等客户端下一条命令，**不在等任何锁**。所以它是链头：判据是「不再等别人」，不是「等得最久」或「语句最显眼」。它同时在 658918 的持锁方名单里、又不在任何等待记录里，两条判据都指向它。

它的最后一条 SQL 是 `update locklab_orders set status = 'A' where id = 1;`，事务已开约 40 秒未提交，行锁一直握着。注意它显示的 SQL 只是「最后执行过的一条」，但这次锁确实来自这条 UPDATE；更关键的是**它拿了锁之后什么都没做**。

典型成因：应用开了事务、改完数据没 COMMIT 就去干别的了（或客户端异常退出，事务悬空）。

## 五、处置建议（只读诊断；下列动作请 DBA 确认后执行）

**首选：结束链头 658916（locklab-A）**
- 代价：它未提交的事务被回滚，`status` 置 'A' 的那次更新丢失（id = 1 回到原值）。这是必须接受的。
- 之后预计：658918 拿到行锁、执行自己的 update；658917 转为等 658918 的事务锁（三段链收成两段）。只要 658918 是正常短事务并提交，658917 随即放行。

**不要结束中段的 658918（locklab-B）**
- 同一行排队时，结束中间会话只是让 C 改为直接等 A 的事务锁，**问题原样存在**，还白白回滚一个正常业务事务。
- 提醒：按「每个等待者的直接阻塞者」自动生成的 kill 名单会同时列上 658916 和 658918，原样执行会多回滚一个事务。**名单必须和拼出来的链头核对后再给 DBA。**

**如果 658918 之后也被发现长期不提交**，说明应用侧存在同类问题，需要连它一起处理，并回到第六节的防复发项。

## 六、置信度：高，但不是满分

支持：三类来源相互独立（服务器日志、锁视图、主机进程表），两条边在三处完全吻合；事务时长严格递减；链头在两条独立判据上同时成立。

为什么不是更高：

1. **连接数对不上 1 条**：连接分布共 4 条（active 3 + idle in transaction 1），主机进程表只有 3 条。最可能是执行本次采集的诊断会话自身（跑 SQL 时它就是 active），但**无证据排除另有第 4 个会话**；因此「不存在第二条并行链」不能算已证明。
2. **只有瞬间快照**：视图反映 18:13:02 这一瞬，日志两个采样点分别为 18:12:55 / 18:12:57。链条更早的形状（例如 C 是否曾直接等 A）无法回溯。
3. **OID 未做目录核对**：relation 19034 / database 13994 是 OID，与视图给出的表名 `locklab_orders` 分别来自两条证据，各自自洽，但没有做 OID → 表名的显式校验。

## 七、下一步只读验证

1. OID 核对：`select 19034::regclass;`，并确认 database 13994 就是当前库。
2. 查第 4 条连接：重跑「连接按状态分布」并列出 pid，看多出来的那条是不是采集会话自己的客户端。
3. 确认是否还有别的锁对象：按 `relation` 分组列出所有 `granted = false` 的锁行。
4. 复核 locklab-A 的应用侧：ClientRead 且无后续命令，通常是客户端没提交就离开了；确认该连接是否已断、下次是否还会复用。

## 八、防复发（应用侧）

- **事务边界收紧**：UPDATE 之后立刻 COMMIT / ROLLBACK，不在事务里做远程调用或等用户输入。
- **设置 `idle_in_transaction_session_timeout`**：让闲置在事务中的会话被自动清理，值按业务最长事务定，先从分钟级起。
- **连接池健康检查**：取用连接前做有效性校验，避免客户端异常退出后事务悬空在库上。
